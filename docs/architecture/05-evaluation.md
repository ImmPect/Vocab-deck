# 5 Оценка архитектуры

Архитектура оценена по четырём критериям из задания. По каждому критерию указано, какие решения его обеспечивают, какие требования ТЗ при этом выполняются, какие есть ограничения и что делать при росте системы.

## 5.1 Масштабируемость

| Решение | Как обеспечивает масштабируемость | Требование ТЗ |
|---|---|---|
| Сервер API без состояния | Сессии, раунды и прогресс хранятся в PostgreSQL, а не в памяти процесса. Любой экземпляр обрабатывает любой запрос, поэтому экземпляры можно добавлять за балансировщиком (горизонтальное масштабирование) | NFR-M-01 |
| Статический фронтенд на CDN | Раздача интерфейса не нагружает сервер API и масштабируется провайдером CDN | NFR-P-01 |
| Индексы под основные выборки | `(user_id, next_review_at)` для входящих, `(user_id, created_at)` для статистики, уникальный `client_event_id` | NFR-M-02 |
| Модульный монолит с границами модулей | Модуль с наибольшей нагрузкой (`learning`) можно выделить в отдельный сервис без изменения API для клиента | — |
| Версионирование API `/api/v1` | Можно подключить мобильный клиент и выпустить `/api/v2`, не ломая веб-клиент | NFR-M-04 |

**Оценка нагрузки.** 10 000 пользователей при 10 % ежедневно активных и средней сессии в 30 ответов — это около 30 000 ответов в день, в пике порядка 5–10 запросов в секунду. С такой нагрузкой справляется один экземпляр FastAPI и одна БД. Таблица `answer_events` растёт примерно на 1 млн строк в месяц, что укладывается в NFR-M-02 без изменения структуры.

**Ограничения и план роста.**
1. Узкое место при росте — единая БД. Первые шаги: реплика PostgreSQL только для чтения (статистика, списки слов) и кэш Redis для редко меняющихся данных (опубликованные колоды, карьерная лестница).
2. Журнал `answer_events` при росте в десятки раз — секционирование по месяцам (partitioning).
3. Если 10-кратный рост придётся на игровую часть, `learning` и `gamification` выделяются в отдельный сервис, а для начисления достижений вводится очередь сообщений: событие «ответ принят» → асинхронная проверка достижений.

## 5.2 Сопровождаемость

| Решение | Как обеспечивает сопровождаемость |
|---|---|
| Деление бэкенда на модули по предметной области (`auth`, `decks`, `learning`…) | Изменение правил игры затрагивает только `gamification`, изменение импорта — только `decks` |
| Одинаковые слои в каждом модуле (router → service → repository) | Новый разработчик сразу знает, где искать HTTP-логику, бизнес-правила и запросы к БД |
| Правила игры собраны в одном модуле `gamification` | Правило «0 опыта за повторный ответ» применяется одинаково к раундам, входящим и перенесённому гостевому прогрессу |
| Feature-Sliced Design на фронтенде | Слои импортируют только нижележащие слои, поэтому фича «импорт CSV» не может сломать «игру» |
| Единый формат ответов и ошибок API | Один обработчик ошибок на клиенте, предсказуемое поведение |
| Типизация: Pydantic на сервере, TypeScript на клиенте, OpenAPI-спецификация `/docs` | Несоответствие контракта обнаруживается при сборке, а не у пользователя |
| Миграции Alembic, версия формата localStorage | Схему БД и формат локальных данных можно менять без потерь (NFR-R-03) |
| Тесты и CI (GitHub Actions) | Сервисы тестируются без HTTP и БД; каждый pull request проверяется автоматически |

**Ограничения.** Модульный монолит требует дисциплины: ничто технически не мешает импортировать чужой репозиторий. Для контроля в CI добавляется проверка зависимостей между модулями (например, `import-linter` для Python и правило `eslint-plugin-boundaries` для слоёв FSD).

## 5.3 Производительность

| Решение | Эффект | Требование ТЗ |
|---|---|---|
| SPA с разделением кода по маршрутам; админка в отдельном чанке | Первая загрузка — только код кабинета, не больше 300 КБ в сжатом виде | NFR-P-04, NFR-P-01 |
| Кэш серверных данных RTK Query | Повторные переходы между экранами не делают лишних запросов | NFR-P-02 |
| Таймер, переворот карточки, подсветка выбора — на клиенте | Реакция на действие пользователя без ожидания сети, не более 100 мс | NFR-P-02 |
| Раунд загружается одним запросом (`POST /rounds` — сразу 5 вопросов) | Между вопросами нет загрузки, только короткий запрос на проверку | — |
| `GET /me` возвращает опыт, должность, серию и число входящих одним ответом | Кабинет открывается за 2–3 запроса | NFR-P-01 |
| Денормализованные `users.xp` и `streak_days` | Не нужно пересчитывать журнал ответов при каждом открытии кабинета | NFR-P-03 |
| Пагинация всех списков (`limit` ≤ 100) | Список из 5 000 слов не загружается целиком | NFR-M-03 |
| Индексы БД (п. 5.1) | Выборка входящих — поиск по индексу, а не полный просмотр таблицы | NFR-P-03 |
| Озвучка через Web Speech API на устройстве | Нет аудиофайлов и запросов к серверу | — |

**Проверка.** LCP кабинета — Lighthouse в режиме мобильного устройства и сети 4G. Время ответа API под нагрузкой 100 одновременных пользователей — Locust, критерий 95-го перцентиля ≤ 300 мс.

**Ограничение.** Проверка каждого ответа в раунде требует запроса к серверу, поэтому при медленной сети опыт показывается с задержкой. Сделано так сознательно: опыт считает только сервер. Чтобы задержка не мешала, выбор подсвечивается сразу, а сервер даёт допуск 5 с к лимиту раунда на задержку сети. Если связь пропала, ответ уходит в очередь и проверяется позже по времени ответа на устройстве (`answered_at`).

## 5.4 Безопасность

| Угроза | Мера защиты | Требование ТЗ |
|---|---|---|
| Перехват данных | Только HTTPS; cookie с атрибутом Secure | NFR-S-01 |
| Утечка паролей из БД | Хранится только хэш Argon2id с солью | NFR-S-02 |
| Кража сессии через XSS | Cookie HttpOnly — недоступна из JavaScript; React экранирует вывод; пользовательские слова выводятся только как текст | NFR-S-03, NFR-S-06 |
| CSRF (запрос с чужого сайта) | SameSite=Lax, обязательный заголовок `X-Requested-With`, CORS только для домена приложения | NFR-S-03 |
| Подбор пароля | Блокировка на 15 минут после 5 неудачных попыток; ограничение частоты запросов по IP; общее сообщение «неверная почта или пароль» | NFR-S-04 |
| Подмена опыта и результатов | Клиент передаёт только ответы; правильные ответы хранятся в `rounds` и не отдаются клиенту; опыт считает `gamification` | NFR-S-05 |
| Подделка гостевого прогресса | Каждый проверенный ответ гостя подписан HMAC; при переносе сервер проверяет подписи и пересчитывает опыт сам | NFR-S-05 |
| Повторная отправка ответа (накрутка) | Уникальный `client_event_id`; 0 опыта за повторный верный ответ на то же слово в тот же день | NFR-R-02 |
| SQL-инъекции | Запросы строит ORM SQLAlchemy с параметрами | NFR-S-06 |
| Вредоносный CSV | Ограничение размера и числа строк, проверка символов, вывод только как текст | NFR-S-06 |
| Доступ к чужим данным и админке | Проверка роли на каждом запросе к `/admin/*`; проверка владельца для личных списков; клиент не имеет прямого доступа к БД | NFR-S-07 |
| Избыточные персональные данные | Хранятся только имя и почта; согласие фиксируется в `consent_at`; удаление аккаунта удаляет ПДн | NFR-S-08 |
| Утечка секретов | Ключи (`SECRET_KEY` для HMAC, `DATABASE_URL`) — только в переменных окружения, не в репозитории | — |

**Ограничения.** Гость может играть и получать опыт только локально, и до регистрации его прогресс не защищён от очистки браузера. Это осознанная плата за вход без регистрации (позиционирование из ТЗ, п. 2.3). Квитанции HMAC защищают от подделки, но не от того, что гость наберёт опыт честно на нескольких устройствах и перенесёт только один журнал. Для учебного приложения это приемлемо.

## 5.5 Итоговая оценка

| Критерий | Оценка | Сильные стороны | Риски и план |
|---|---|---|---|
| Масштабируемость | Достаточная для целевой нагрузки с запасом | Stateless API, CDN, индексы, версия API | Единая БД — реплики, кэш Redis, секционирование журнала |
| Сопровождаемость | Высокая | Модули по предметной области, одинаковые слои, FSD, типизация, CI | Контроль границ модулей автоматической проверкой |
| Производительность | Соответствует NFR-P | Разделение кода, кэш RTK Query, денормализация, пагинация | Задержка проверки ответа на медленной сети — мгновенная подсветка выбора, допуск 5 с, очередь ответов |
| Безопасность | Высокая для данного класса приложений | Расчёт результатов только на сервере, HttpOnly-сессии, Argon2id, HMAC-квитанции | Гостевой прогресс до регистрации хранится только локально |

Выбранная архитектура — трёхуровневая система с SPA, модульным монолитом на FastAPI и PostgreSQL. Она соответствует размеру проекта (принцип KISS) и выполняет нефункциональные требования ТЗ. Ключевое решение, на котором держатся безопасность и честность игровой механики, — «сервер — единственный источник истины об опыте». Путь развития до микросервисов определён заранее и не требует переписывать клиент.
